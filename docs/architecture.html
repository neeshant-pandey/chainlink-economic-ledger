Chainlink Economic Ledger

Reconstructs LINK token movements for Staking v0.2 and Payment Abstraction from raw Ethereum artifacts. ABI-driven decoding in Python, internal-trace walking, EIP-1967 proxy probing, N:M reconciliation, and a double-entry economic ledger exposed through dbt.

Stake fixture 0x08c2902756cb… block 18,671,459 PA fixture 0x92359883d1f3… block 24,139,066 293 unit tests · 73 dbt tests · end-to-end local DuckDB build

Production pipeline

Ethereum mainnet → BigQuery crypto_ethereum → Python decoder, semantics, and reconciler → BigQuery raw datasets → dbt marts → Economics-team consumers. Airflow orchestrates; Databricks materializes a parity Delta layer; lineage tags every row with a deterministic run_partition_id.

The four moves that put this past "Dune analyst"

The recruiter note's literal phrase was "beyond basic RPC-based blockchain querying". Each card below is a concrete move from the pipeline that demonstrates it.

Move 1 · Decoder

Hand-decoded raw EVM bytes

eth_abi.decode on topics[1:] + data. No web3.py contract wrappers, no deployed-contract instance required. Historical events decoded directly from wire format.

Move 2 · Trace walking

Trace-tree + ancestor-success filter

BigQuery's flat trace_address rows are reconstructed into a nested call tree. A movement is emitted only when call.success ∧ every_ancestor.success ∧ tx.status == 1.

Move 3 · Proxy probing

EIP-1967 verified-negative

Probed the three PA contracts via eth_getStorageAt on the impl, admin, and beacon slots. All three returned 0x000…0 — they are not proxies. Disclosed as a verified negative.

Move 4 · Reconciliation

N:M with Status × Method

match_action_to_movements returns list[Match], never Transfer | None. An action maps to 0, 1, or many movements. Ambiguity is surfaced, not silenced.

Seven deterministic ID grains

Every entity has a pure sha256(canonical_key) ID. Replays produce identical IDs and therefore identical row hashes. No UUIDs, no time.time(), no Python hash() (PYTHONHASHSEED).

Reconciliation model

Action ↔ Movement is a bipartite graph. Each edge carries a Status and (when meaningful) a Method. Per-tx and per-partition rollups feed the reconciliation_status mart.

Data quality

Reconciling raw chain artifacts against economic claims only works if every layer fails loudly. Quality is categorized by what each test class catches — schema shape, source liveness, accounting invariants, and cross-warehouse drift.

Layer 1 · Schema tests

dbt generic tests

not_null, unique, accepted_values, and relationships enforce fact → dim referential integrity. event_id, action_id, and ledger_entry_id are guaranteed unique and non-null because each is a deterministic sha256(canonical_key) hash.

Layer 2 · Freshness

Source freshness on chain partitions

dbt source freshness on raw chain partitions with warn_after: 1 hour and error_after: 6 hours. Reorg-aware: freshness is measured from finalized block time, not wall clock, so a quiet RPC doesn't masquerade as stale data.

Layer 3 · Invariants

Singular tests with economic meaning

assert_ledger_balanced_per_tx.sql enforces debits == credits per tx. Other gates: unknown-signature ratio threshold, reconciliation pass-rate floor, per-tx LINK conservation, and monotonic block height across partitions.

Layer 4 · Cross-warehouse parity

Databricks Delta parity

The Databricks parity notebook hashes mart rows and diffs row counts against the BigQuery marts. Catches silent divergence between warehouses — schema drift, late-arriving rows, or a mart that rebuilt on only one side.

73 dbt data tests · 293 Python unit tests · invariant gates · cross-warehouse parity check — the full quality envelope from wire-level decode to consumer mart.

Scalability

The deliberately small dataset (~500 MB, two real mainnet tx fixtures) exists to demonstrate structural complexity. The levers below are how this pipeline grows from the local fixture path to a billion-row production workload without rewriting.

Today's scale ~500 MB · 2 tx fixtures

Local DuckDB end-to-end · 2 fixtures · seconds to rebuild
  • Two real mainnet txs decoded end-to-end: stake + PA Reserves deposit
  • 29 dbt models · 73 data tests · 293 Python unit tests
  • DuckDB locally for parity with BigQuery semantics
  • Volume is tiny on purpose — the point is the decode + reconcile shape

At production scale billions of logs · multi-chain

BigQuery + GCS parquet · partitioned + clustered raw layer
  • Raw chain tables partitioned by DATE(block_timestamp); clustered by contract_address, tx_hash
  • Incremental dbt models: materialized='incremental', unique_key='event_id', incremental_strategy='insert_overwrite' on the partition column
  • Bounded backfills: one partition per task; cost capped by partition pruning instead of full scans
  • GCS parquet as the durable raw layer; BigQuery re-materialized cheaply on demand
  • BigQuery slot reservations when steady-state cost exceeds on-demand breakeven (~100 slot-hours sustained)
  • Trace-tree builder is per-tx, embarrassingly parallel — fans out across Airflow workers

The local path proves correctness; the production levers above are designed but not load-tested against billions of rows. The shape is right.

Retention

Raw chain artifacts are forever; warm marts are forever; the layers in between are tiered for cost. Deterministic replay means we never need a stale staging snapshot — we can always rebuild from raw.

LayerRetentionStorage class / mechanismWhy
GCS raw parquet forever Standard → Nearline 30d → Coldline 90d → Archive 365d durable source of truth; cheap once cold
BigQuery raw tables 90-day partition expiration · 7-day time travel PARTITION BY DATE(block_timestamp) queryable hot tier; rebuildable from GCS
BigQuery intermediate 30-day partition expiration auto-expire via partition_expiration_days derived; always rebuildable from raw
BigQuery marts (marts.*, analytics.*) forever dbt snapshot monthly for SCD2 history economics-team contract; preserved
Run lineage (run_partition_id) forever append-only ledger table; never deleted required for replay debugging and audit trail
dbt artifacts (manifest.json, run_results.json) 90 days GCS bucket lifecycle diagnostic; not part of the data product

Raw and marts are durable; everything in between can be rebuilt from raw via deterministic replay. This bounds storage cost without locking the team out of historical states.

Output: marts the Economics team queries

Marts are named for the economic question they answer, not for table mechanics. Every mart is dbt-contracted, freshness-checked, and tagged with run_partition_id for replay lineage.

marts.ledger_entries
Double-entry economic ledger. Debits == credits per tx enforced as a dbt invariant.
marts.staking_link_flows
One row per stake / unstake / reward event with reconciliation status.
marts.reconciliation_status
Per-partition pass rate and counts by status. Powers the recon dashboard.
marts.wallet_economics
Per-wallet aggregate LINK in / out / net by protocol surface.
marts.pool_economics
Per-pool inflow, outflow, principal delta, reward outflow.
analytics.weekly_reserve_accumulation
PA Reserve LINK growth per week, split by inflow source.
analytics.apy_realized_by_pool
Daily reward-yield proxy. Disclosed as proxy, not true TWAP-APY.
analytics.fee_attribution_by_source
PA fee inflow by Chainlink service: VRF / Functions / Data Streams / CCIP.
analytics.staker_reward_sustainability
Reward outflow vs Reserve inflow per snapshot. Flags unsustainable days.
